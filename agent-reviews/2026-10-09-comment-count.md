# 2026-10-09: queue comment count includes thread comments, and a legend for the marks (#165)

**Worked:** the schema file GitHub publishes (`schema.docs.graphql`) settled what could be settled offline: `PullRequest.comments` is an `IssueCommentConnection` (general comments only) and `totalCommentsCount` is a nullable `Int` described only as "a count of how many comments this pull request has received". Both fit the screenshot (a general-only count, or a null read as zero by `unwrap_or(0)`), so the fix doesn't depend on which it was. One definition (`rb_core::thread_comment_count`, `Signals::reconcile`) feeds the Conversation tab and the queue row. The first version read a comment count under each thread and cost about 29 points a page; the maintainer decided not to raise the rate-limit cost, so the list now reads only free `totalCount`s on connections it already requests (`comments`, `reviewThreads`) and shows a lower bound `¶N+` (general comments plus one per thread) whenever threads exist, exact `¶N` otherwise, and the exact total once the selected change's threads load. The legend is drawn as its own section of the help overlay with its own key column, because a 10-cell key column would have clipped the longest existing help labels.

**Friction:** the per-thread count is the expensive shape for GitHub's rate-limit formula (a connection under each thread under each change), which is why it was dropped; the cost test now pins the old 401 requests and 8,150 nodes. The demo's `comments = 6` override disagreed with its three threads once the selected row took the loaded total, so it was removed. The help tests first failed on Windows because the Unix-overlay override applied to drawing but not to key handling (nextest runs each test in its own process, so a global set during render isn't set yet during `j` presses); the override now applies in `press` too and scrolling stops when it stops moving.

**Not verified:** real GitHub or GitLab responses (all fixtures are shaped from the documentation), whether `totalCommentsCount` was null or a general-only count in the screenshot, the GraphQL cost (calculated from the query, not read from a live `rateLimit`), and GitLab's `user_notes_count` excluding system notes (from GitLab's documentation and source as remembered, not observed).
