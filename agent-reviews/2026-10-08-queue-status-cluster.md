# 2026-10-08: queue rows show review state, comments, open threads, size and CI (#162)

**Worked:** the model already held most of it (`reviewers`, `adds`, `dels`, `files`, `ci`), so the new data is one small `Signals` struct on `ChangeSummary` with a serde default, which kept every other constructor to a single added line and old cache rows loading without a migration. Computing the tally in the providers (where the viewer's login is known) kept "other people's reviews" out of the UI, which only reads numbers. Making the cluster a list of fixed-width pieces with a pure `plan` and `segments` made the drop order, alignment and wording unit-testable without a terminal. The 48-column default Queue has no room for it beside Detail, which the narrow-width tests pin as designed behaviour rather than a bug.

**Friction:** GitLab's list endpoint has no approvals and no line counts, and only a resolved flag for threads, so the cluster is thinner there until the details load; the details now travel with `ChangeInfo.summary` and the row reads them when present. Showing every state in the demo meant adding other people's reviewers to two fixture changes, which moved their Reviewers list in the detail snapshots; the default-selected change was left alone to keep that churn small. Most dashboard snapshots moved because queue rows appear in them, so a script checked that every changed line only filled previously blank cells, and the remainder (Reviewers lists, the `NO_COLOR` modifier dumps) was read by hand. The pty tests `pty_show` are flaky on a busy machine (they fail on `main` too).

**Not verified:** real GitHub or GitLab responses (the mapping is tested against wiremock fixtures shaped from the API docs), `totalCommentsCount` semantics on a live repository, and the GraphQL cost figure, which is calculated from the query rather than read from a live `rateLimit` response.
